## Хэсэг A: Category-Partition (гараар) — `POST /transfer`

### Давуу эрэмбэ

Нэг хүсэлтэд хэд хэдэн алдаа зэрэг байвал дараах дарааллаар **эхний таарсан алдааг** буцаана гэж үзнэ:

`NO_FROM → FROZEN → NO_TO → SAME_ACCOUNT → BAD_AMOUNT → INSUFFICIENT → LIMIT`

Үндэслэл: эхлээд данс бүр системд байгаа эсэх, дараа нь from данс ашиглах боломжтой (царцаагдаагүй) эсэхийг шалгана. Үүний дараа дансны холбоо (to ≠ from), дараа нь дүнгийн утгын зөв байдал (amount > 0) шалгагдана. Үлдэгдэл, лимитийн шалгалт зөвхөн хүчинтэй данс, хүчинтэй дүн дээр утгатай тул хамгийн сүүлд ордог. INSUFFICIENT нь LIMIT-ээс түрүүлнэ, учир нь дансны өөрийн үлдэгдэл (хөрөнгийн хүрэлцээ) нь нэмэлт хязгаар болох өдрийн лимитээс илүү үндсэн нөхцөл.

balance, limit_left-ийн алдааны сонголтыг `[ERROR]` биш `[IF]` болгосон. Учир нь `[ERROR]` нь нэг удаа л тестлэгдэх бөгөөд INSUFFICIENT ба LIMIT зэрэг гарах давхар нөхцөл (A3 #16) алга болно.

**Тооны тооцоо:**

- Бүрэн олонлог: 3 × 3 × 4 × 2 × 3 × 3 = **648**
- Хязгаарлалтын дараа: 7 (нэг удаа тестлэх: from 2, to 2, amount 0 ба сөрөг 2, amount 0.01 нэг) + 18 (1 × 1 × 1 × 2 × 3 × 3) = **25**

**648 → 25**

## Хэсэг B: PICT — pairwise covering array

PICT-ийг `~/tools/pict`-д эх кодоос бүтээсэн (хувилбар: `results/pict-build.txt`). Бүх ажиллуулалт анхдагч (`/r`-гүй) тул үр дүн давтагдана.

### B1 — Лекцийн браузерын жишээ

| Хүрээ | Мөрийн тоо | Файл |
|---|---|---|
| 2-way (pairwise) | **10** | `results/browser-2way.txt` |
| 3-way (`/o:3`) | **20** | `results/browser-3way.txt` |
| Бүрэн олонлог (3·3·2·2·2·2) | 144 | — |

**2-way:** 10 мөр гарсан, лекцийн гар шийдэл 9 мөр. Content × Cookies хоёр параметр тус бүр 3 утгатай тул 3 × 3 = 9 өөр хос байх бөгөөд нэг мөр нэг л ийм хос хамарна. Иймд 9 нь онолын доод хязгаар бөгөөд лекцийн гар шийдэл оновчтой, PICT нэг мөрөөр илүү гаргасан. PICT нэг мөр нэмэх бүрт тухайн мөчид хамгийн олон шинэ хос хамарах мөрийг сонгодог greedy алгоритм бөгөөд хамгийн цөөн мөрийг олохыг баталгаажуулдаггүй. Хамгийн бага covering array олох нь тооцооллын хувьд хэцүү бодлого тул PICT хурдан, хангалттай сайн (ойролцоо) шийдэл өгдөг ч оновчтой 9-д үргэлж хүрэхгүй. Харин хос бүр хамрагдсан гэдэг баталгаа хэвээр.

**3-way:** 20 мөр нь бүрэн олонлогийн 144-ийн ойролцоогоор 14% (86%-иар цөөн). Гурвалсан хамаарал хүртэл хамруулсан мөртлөө тестийн тоо үлэмж багассан.

### B2 — Шилжүүлгийн модель

Моделийн параметрүүд нь A1-ийн сонголтууд. balance, limit_left далд сонголтуудыг Amount-ын `OverBalance` / `OverLimit` утгад нэгтгэсэн тул PICT-ийн модель дөрвөн параметртэй.

**Model файлууд:** `transfer-nc.model` (хязгаарлалтгүй), `transfer.model` (A2-ын хязгаарлалттай), `transfer-neg.model` (`~`-тэй).

```
# transfer-nc.model
From:     Valid, Frozen, Missing
To:       Valid, Missing, SameAsFrom
Amount:   Zero, Normal, OverBalance, OverLimit
Currency: Same, Different
```

```
# transfer.model
From:     Valid, Frozen, Missing
To:       Valid, Missing, SameAsFrom
Amount:   Zero, Normal, OverBalance, OverLimit
Currency: Same, Different

IF [From] <> "Valid" THEN [Amount] = "Normal";
IF [To] <> "Valid" THEN [Amount] = "Normal";
IF [From] <> "Valid" THEN [To] = "Valid";
```

```
# transfer-neg.model
From:     Valid, ~Frozen, ~Missing
To:       Valid, ~Missing, ~SameAsFrom
Amount:   Normal, ~Zero, ~OverBalance, ~OverLimit
Currency: Same, Different
```

`transfer.model`-ийн хязгаарлалтууд (A2-оос):

- `IF [From] <> "Valid" THEN [Amount] = "Normal";` — from буруу бол дүнгийн алдааг хамт тестлэхгүй (error masking).
- `IF [To] <> "Valid" THEN [Amount] = "Normal";` — to буруу бол мөн адил.
- `IF [From] <> "Valid" THEN [To] = "Valid";` — from-ийн алдаа to-ийн алдаатай хамт орохгүй (A2-ын `[ERROR]` нэг удаа). Энэ гуравдахь хязгаарлалтыг дээрх хоёрыг нэмж өөрөө оруулсан.

**Гаралтыг уншсан дүгнэлт**

- **Хязгаарлалтгүй:** happy path 1 мөр гарсан боловч 13 мөрийн 11-д нь 2-3 алдаа зэрэг байна (жишээ нь `Missing, Missing, OverBalance, Different`). Эхний алдаа бусдыг нууна, мөн From = Missing үед OverBalance-ийн үлдэгдэл гэж байхгүй тул мөр утгагүй. Иймд олон алдаатай мөр юуг шалгаж байгаа нь тодорхойгүй, зөвхөн давуу эрэмбээс хамаарна.
- **Хязгаарлалттай:** нэг мөрөнд яг нэг алдаа, мөр бүр нэг алдааны ангийг шалгана. Гэхдээ happy path мөр гарсангүй. Pairwise нь `(Valid, Valid, Normal)` гурвалыг шаарддаггүй, Valid–Valid хос нь OverBalance зэрэг алдаатай мөрөөр хамрагдсан тул PICT нэмэлт мөр өгөөгүй. Иймд happy path-ийг гараар нэмэх шаардлагатай.
- **Мөрийн тоо:** хязгаарлалттай (14) нь хязгаарлалтгүйгээс (13) олон болсон. Хязгаарлалт нь утгагүй хослолыг хасах бөгөөд мөрийн тоог багасгах зорилготой биш. Үлдсэн боломжит хосуудыг бүрэн хамрахын тулд PICT нэмэлт мөр өгсөн.
- **`~`-тэй:** мөр бүрт хамгийн ихдээ нэг сөрөг утга орсон (A2-ын `[ERROR]`-той дүйнэ), happy path 2 мөр (Same / Different валюттай) гарсан.

**`~` хэрэглэхэд A2-ын хязгаарлалт хэрэгтэй хэвээр үү?** Энэ моделийн хувьд A2-ын `[ERROR]`-той холбоотой гурван хязгаарлалт шаардлагагүй болсон, учир нь `~` нь нэг мөрөнд нэг л алдаа оруулдаг. Харин хоёр зүйл хэвээр хэрэгтэй:

1. A2-ын `[IF]` хязгаарлалт (жишээ нь balance, limit_left-ийг тусад нь параметр болговол "алдаа нь зөвхөн бусад оролт хүчинтэй үед" гэсэн хязгаарлалт).
2. Давхар нөхцөл `~`-тэй моделд огт орохгүй (нэг мөрөнд хоёр сөрөг утга гарахгүй). Тиймээс A3-ийн #16, #18, #19-ийг гараар нэмж, давуу эрэмбээр oracle-ыг нь тогтооно.

## Дүгнэлт

Category-partition (A) нь алдааны семантикийг сайн барьдаг: алдаа бүрийн хүлээгдэх үр дүн, давхар нөхцөл, давуу эрэмбийг тодорхой гаргадаг. PICT (B) нь хосын хамралтыг алгоритмаар баталгаажуулж, хурдан үүсгэнэ (3-way: 144 → 20). Харин PICT алдааны семантикийг өөрөө ойлгодоггүй: хязгаарлалтгүй үед 13 мөрийн 11-д нь 2-3 алдаа зэрэг орж, error masking үүссэн. `~` нь нэг мөрөнд нэг алдаа болгож A2-ын `[ERROR]`-ыг орлосон ч давхар нөхцөл моделоос алга болсон тул түүнийг гараар нэмэх хэрэгтэй. Хязгаарлалттай хувилбарт happy path мөр гарахгүй байсан нь pairwise нь "бүх утга хүчинтэй" мөрийг шаарддаггүйг харуулсан. Мөн хязгаарлалт нэмэхэд мөрийн тоо цөөрөхгүй байж болохыг (13 → 14) харсан. Тиймээс хоёр аргыг хослуулах нь зөв: PICT-ээр хослолын хамралтыг, A3-аар happy path, давхар нөхцөл, хөрвүүлэлтийн хязгаарыг баталгаажуулна. Хамгийн их бодол шаардсан алхам нь давуу эрэмбийг тогтоох ба далд balance, limit_left-ийг PICT-ийн Amount параметрт нэгтгэх явдал байсан, учир нь тэгэхэд INSUFFICIENT ба LIMIT зэрэг гарах давхар нөхцөл моделд тусгагдахгүй болсон. Хөрвүүлсний дараах шалгалт (A3 #17, TC2) нь тодорхойлолтоос шууд харагдахгүй, тусгайлан анхаарах шаардлагатай байсан. Кодгүй, зөвхөн тодорхойлолтоос тест зохиох нь (shift-left) спецификацийн цоорхой (үл мэдэгдэх валютын кодын боловсруулалт тодорхойгүй байх) илрүүлэхэд тусалсан.
